# 项目台账

一个项目一个 `.xlsx` 文件。每次有新信息(会议、电话、微信、临时安排)就合并进去,
而不是另起一份纪要。判断依据:使用者要知道的是"这个项目现在是什么状态",单次纪要
回答不了这个问题。

写表用 `xlsx` 技能(`skills/xlsx/SKILL.md`),本技能只规定表的结构和合并规则。

## 文件布局

```
<项目名>-台账.xlsx
├── 事项        主表,一行一个事项
├── 变更日志    每次改动一行,记下改了什么、依据哪次沟通
└── 待决事项    需要别人决定或答复的事,与主表分开
```

三张表都要有,缺一张就会丢掉信息:只有主表时,"这条为什么从进行中变成搁置"无处可
查;没有待决事项表时,等别人答复的事会混在自己的待办里,看不出卡在哪。

## 主表列

| 列       | 说明                                                               |
| -------- | ------------------------------------------------------------------ |
| 事项     | 一句话说清要做什么。不写"推进设计",写"向设计院提交总平面图初稿"    |
| 项目     | 同一文件内只有一个项目时可省                                       |
| 阶段     | 属于哪个阶段的工作                                                 |
| 负责人   | 实际推进的人                                                       |
| 交办人   | 谁提出或交办的。与负责人分开记:责任边界不清是这里要解决的问题之一  |
| 截止     | `YYYY-MM-DD`。没有正式期限就留空,不要填推测值                      |
| 状态     | 见下方枚举                                                         |
| 阻塞对象 | 在等谁/等什么。状态是"等…"时必填                                   |
| 完成依据 | 凭什么算完成(交付物、对方书面确认、验收记录)。空着表示完成标准未定 |
| 来源     | 哪次沟通带来的,如"2026-10-28 园区现场会"                           |
| 确认状态 | `已确认` / `待确认`。见下方                                        |
| 更新人   | 最后改这行的人                                                     |
| 更新时间 | `YYYY-MM-DD HH:MM`                                                 |

## 状态枚举

只用这几个值:

- `未开始`
- `进行中`
- `等外部反馈` — 在等设计院、园区、供应商等外部单位
- `等内部决定` — 在等公司内部拍板,但不必是领导
- `等领导批示` — 必须领导本人决定
- `已交材料` — 自己这边已交付,等对方处理
- `已完成`
- `已搁置`

把"等外部反馈""等内部决定""等领导批示"分开,是因为三者的推进动作完全不同:一个要
催外部,一个要内部协调,一个要把事项写进汇报等答复。合并成一个"等待中"就看不出该
做什么。`已交材料` 与 `已完成` 也不能合并:交出去不等于对方接受。

## 确认状态

只有两个值,不要自己增加第三种:

- `已确认` — 有书面依据,或当事人明确说过
- `待确认` — 其余全部

把口头听来的、推测的、从一方说法里推断出来的,一律写 `待确认`。这不是谨慎,是因为
客户场景里大量字段本身尚未定下来(谁可以调整负责人和完成状态、工作完成的判断依据、
历史进度保留多久、哪些决定属于领导),把它们填成确定值会让台账看起来已经对齐,实际
没有。遇到这类空缺:写进「待决事项」表,**不要**在主表里替使用者作决定。

## 合并新信息的步骤

1. 先读现有台账。没有读过就不要写 —— 整表覆盖会丢掉上一次的来源和变更日志。
2. 从新材料里抽出事项,逐条与主表比对:
   - 主表已有且无变化 → 不动
   - 主表已有且有变化 → 改主表,并在「变更日志」加一行(旧值 → 新值 + 来源)
   - 主表没有 → 新增一行,`来源` 填这次沟通
3. 同一事项在不同沟通里结论不同时,主表取最新,「变更日志」保留前一个结论和它的
   来源。不要把旧结论删掉:谁在什么时候改了口径,是使用者要查的事。
4. 需要别人决定或答复的,写进「待决事项」表,并在主表对应行把状态置为对应的"等…"。
5. 本次没有涉及的行一律不动,包括不要刷新它们的 `更新时间`。

## 变更日志列

`时间` `事项` `字段` `原值` `新值` `依据/来源` `更新人`

## 待决事项列

`事项` `类别` `需要谁决定` `可选方案` `期望答复时间` `状态` `答复` `提出时间`

`类别` 取 `只需知情` / `需要批准` / `专业判断` 之一。这三类的处理方式不同:只需知情
的不要放进等待队列;专业判断的不要上报等批示。

这张表的 `状态` 用 `待答复` / `已答复` / `已撤回` 三个值,不要复用主表的状态枚举
—— 主表记的是"事情做到哪一步",这里记的是"问出去的话有没有回音",两者不是一回事。

## 输出预算

合并一次沟通的输出量比想象的大:一份九行的台账加上变更日志,整表重出约 6700 个
输出 token(2026-11-02 实测)。输出上限不足时模型会在表格中途截断,而截断的表格
看起来像一份完整的台账 —— 少掉的行不会有任何提示。

所以:合并时把输出上限放到 8000 以上;如果只需要改两三行,就明说"只输出变动的行
和对应的变更日志",不要每次都整表重出。

## 不要做的事

- 不要为了让表看起来完整而填推测值。空单元格是"不知道",填了就是"知道"
- 不要把一次沟通整理成一个新文件。项目台账是累积的
- 不要在主表里删行。不做了就把状态改成 `已搁置`,并在变更日志写原因
- 不要自己设定截止时间。没有正式期限就留空,并在待决事项里问
